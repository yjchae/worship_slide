## ① 판정 요약

**판정: 수정 필요 (구현 착수 전에 문서를 하나로 맞춰야 함)**

- 기능 방향(코드는 관객 화면·PPTX·통역(B)에 안 내보냄, `lyrics` 는 그대로, 코드는 새 칸, DB v20)은 세 문서가 같다. 문서에 적힌 코드 사실도 거의 다 맞다 — 함수 이름 약 80개와 줄 번호 표본(`_SlideInfo` 81, `_allSlides` 896, `_buildSlidePageData` 1123, `_buildSingerViewData` 1291, `_singerDedupeKey` 1965, `_songWithPages` 3821, `itemsFromPages` 10669, `ConsoleSlideView` 10716, `_pageDataFor` 13022, `export_presentation` 1988, `lyric_line_boxes_by_system` 2314, `erase_staff_symbols` 2916, `is_chord_line` 2453, `resolve_sheet_lines` 3127, `_native_page_lines` 3248, `python_bridge.dart exportPresentation` 310, `portableItemRow` 700, `_songKeys` 557)이 실제 코드와 맞았다.
- 하지만 **저장 칸·JSON·동기화 모양이 세 문서에서 모두 다르고**, 아래 '높음' 결함 7개는 이대로 구현하면 데이터를 잃거나(코드 저장 안 됨, 조 값 사라짐), 코드가 엉뚱한 음절에 붙거나, 관객 가사가 몰래 바뀐다.
- 화면(PNG)은 기획서 화면 목록(S1·S1b·S1c·S2~S7)과 1:1 로 맞는다. 다만 싱어·발표 보기 화면이 **원본 줄과 보조 줄을 한 줄씩 엇갈려** 그려 놓았는데, 이는 지금 싱어 배치(본문 덩어리 → 보조 덩어리)와도 데이터 구조와도 다르다(결함 M1).

## ② 팀장 지적 충돌 — 판정과 추천

### 충돌 1. 발표 보기 코드 표시 (기획 D4-A 바꿔 그리기 vs 프론트 (A) 같은 TextPainter 위에 덧그리기)

**판정: 기획 D4-A 를 택한다. 프론트 (A) 덧그리기는 쓰지 않는다.**

- 덧그리기의 겹침은 실제 수치로 확인된다. `slide_text_layout.dart:25` `_mainHeight = 1.25` 이므로 줄 사이 빈 높이는 글자 크기의 약 0.25배뿐이다. 프론트가 제안한 코드 글자(본문 × 0.45)는 그 틈보다 크다. 한글 글자는 em 상자를 거의 다 채우므로 코드가 **윗줄 글자 아래쪽 위에 그려진다**. 반투명 알약을 깔면 윗줄 가사를 가린다. 프론트 문서도 위험 6에서 이것을 인정한다.
- 프론트가 기획안을 반대한 이유는 좌표다. 바꿔 그리면 확대·포인터 좌표가 관객 화면과 달라진다(`_emitPointer`). 그런데 기획 S4 가 이미 "코드 보기 중 영역 확대·포인터 흐리게"로 이것을 막는다.
- 추천 조건(기획서 S4 에 적어 넣을 것):
  1. 코드 보기가 켜진 동안 현재 슬라이드 칸 위의 마우스 이동은 `_emitPointer` 를 **부르지 않는다**(도구를 흐리게 하는 것만으로는 모자라다 — 포인터 모드가 켜진 채 코드 보기를 켠 경우).
  2. 구석의 관객 화면 작은 그림은 지금 `ConsoleSlideView`/`SlideRenderView` 를 **그대로** 쓴다. 코드 인자를 아예 받지 않는 위젯이어야 한다.
  3. 코드 악보 위젯(`ChordSheetView`)은 `SlideRenderView` 에 인자를 더하는 방식이 아니라 **따로 만든 위젯**으로 둔다. 그래야 썸네일·`LyricsOverlayRenderer`·`PageComposer` 가 실수로 코드를 그릴 길이 없다.
  4. 그래도 읽기 어렵거나 조작자가 쓰지 않으면, 프론트 (C)(옆 패널)로 물러선다. (C)를 2순위 대안으로 기획서에 남긴다.
- 함께 정할 것: 오른쪽 '다음 슬라이드' 칸. 기획 S4 와 s4.png 는 코드 악보로 그리고, 프론트 2.3 은 "다음 작은 상자에는 안 그림"이다. → 기획대로(코드 보기 켜짐 = 다음도 코드 악보) 하고 프론트 문서를 고친다.

### 충돌 2. 찬양 동기화 (기획: `SyncSong.chord_lyrics` + 키 없음 = 모르는 PC / 백엔드: 스냅샷 별도 `chords` 구역 + 코드 전용 시각)

**판정: 백엔드안을 택한다.**

- 기획안의 문제
  - 코드만 고쳐도 곡 `updated_at` 이 오른다(기획 3-7). 그러면 다른 PC 에서 같은 때 고친 가사 수정을 이겨 버린다. 백엔드 3.1-4 가 지적한 가사 수정 유실이다.
  - 기획 3-7 은 "동기화 합치기에서도 `realignChords`"를 부른다. 이때 다시 맞춘 결과에 곡 시각을 올리는지가 정해져 있지 않다. 올리면 받기만 한 PC 가 그 곡의 '최신 판'이 되어 다시 퍼뜨리고, 안 올리면 PC 마다 다시 맞춘 결과가 따로 논다.
  - `tieKey`(sync_snapshot.dart:70 = `contentKey\0fileName`)에 코드를 붙이면 같은 시각일 때 판정은 갈린다. 하지만 '키 없음' 판(옛 앱)을 이긴 판으로 볼지 진 판으로 볼지에 따라 결과가 달라져 테스트할 경우의 수가 많다.
- 백엔드안의 장점: 곡 시각·`contentKey`·`content_hash`·`tieKey` 를 그대로 둔다. 옛 앱은 `chords` 를 모르고 지나갈 뿐 코드를 지울 길이 없다.
- 백엔드안에 더해야 할 것
  1. `_songKeys`(sync_service.dart:557)에 `'chords'` 를 넣는다. 지움을 따로 실으면 `'chord_deleted'` 도 넣는다. 빠뜨리면 '안 올린 수정'이 안 잡힌다.
  2. 켤 때 확인(`preview`)의 "바뀐 찬양" 수에 코드만 바뀐 곡을 넣을지 정한다. 추천: 넣는다(그 곡 1개로 센다).
  3. 다른 PC 가 가사를 바꿔 이쪽 코드가 어긋나면 어떻게 하는가. 합칠 때는 코드 글을 **고치지 않는다**(stale 로 둔다). 편집 화면에서 다시 맞추게 한다. 합칠 때 자동으로 다시 맞추면 PC 마다 결과가 달라져 서로 덮어쓴다.
- 기획서 §0 '동기화·저장' 줄과 §3-3·§3-7 을 백엔드안으로 고쳐 쓴다.

### 충돌 3. 정합성 단위 (프론트: 페이지마다 검사 후 그 페이지 코드 버림 / 백엔드: 곡 단위 검사·숨김·작은 변경은 자동 저장 / 기획: `realignChords` + 그 페이지만 숨김)

**판정: 세 겹으로 합친다. 기획을 바탕으로, 백엔드의 '지우지 않음'을 따르고, 프론트의 페이지별 검사를 표시 직전 안전장치로 쓴다.**

| 겹 | 규칙 | 따른 문서 |
|---|---|---|
| 저장 데이터 | 코드 글은 **지우지 않는다**. 다시 맞추기(`realignChords`)가 "확실한 경우"에만 자동으로 저장한다 — 줄이 모두 같고 페이지 경계만 바뀜, 또는 바뀐 글자가 일정 비율 이하. 그 밖에는 고치기 전 글을 그대로 두고 편집 창이 제안만 한다 | 백엔드 2.1·2.2 |
| 곡 상태 | `stripChords(chord) == lyrics`(정규화 후)이면 정상, 아니면 '코드 확인 필요'. 칸에 상태를 저장하지 않고 읽을 때 계산한다 | 백엔드 2.1 + 기획 3-4 |
| 표시 | 곡 상태가 어긋나도 **페이지마다** `strip(코드 페이지) == 원본 페이지` 이면 그 페이지 코드는 보인다. 안 맞는 페이지만 숨긴다. '코드 확인 N' 의 N = 숨긴 페이지 수 | 기획 D2-A, 프론트 1.2-2 |

- 프론트 3-3("평소 모드 저장 시 안 맞는 페이지 코드를 **버린다**")은 지운다. 이는 D2-A·백엔드 2.1 과 어긋나는 데이터 손실이다.
- 백엔드 2.1 의 "싱어·발표자 화면은 코드 없이"를 곡 단위로 읽으면 D2-B(곡 전체 숨김)가 된다. 위 표처럼 페이지 단위로 고쳐 적는다.
- 페이지 짝짓기는 `stripChords` 뒤의 페이지 수가 `lyrics` 페이지 수와 같을 때만 인덱스로 한다. 다르면(빈 줄이 다른 곳에 끼임 등) 전부 숨긴다. 이 규칙을 기획 3-4 에 넣는다.

### 충돌 4. 코드 색 (기획 `#FFC857` vs UI `#FFA94D`, 그리고 프론트 CSS 예시 `#7fd1ff`)

**판정: `#FFA94D` 를 택한다. 같은 값을 네 렌더러에 상수로 넣는다. 단 싱어 머리줄의 조 표시는 다른 색으로 한다.**

- 지금 싱어 보조 줄은 `#ffd54f` 다(singer_web_server.dart:613, MainFlutterWindow.swift:1021). `#FFC857` 은 이와 거의 구분되지 않는다. 같은 화면에 보조 줄과 코드 줄이 같이 나오므로 쓰면 안 된다.
- **충돌이 셋**이다. 프론트 2.1 CSS 예시는 `.seg>b{color:#7fd1ff}`(하늘색)다. 프론트 문서도 고친다.
- 새로 찾은 문제: 싱어 시계는 목표 80% 를 넘으면 `#ffb547`(주황, singer_web_server.dart:587, Swift:1009)이 된다. 그런데 s2·s4 는 조 표시 배지 `A (원래 G, +2)` 를 시계 바로 옆에 주황(`--chord`)으로 둔다. 시간 경고와 헷갈린다. → 조 배지는 회색 테두리 등 중립색으로 바꾸거나, 시계와 떨어뜨린다.
- '다음 페이지'(dim)용 어두운 코드 색도 하나 정한다(Windows `dim` 규칙, 프론트 2.2).
